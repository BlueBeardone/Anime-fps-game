# Physics Movement + Rebindable Input — Design

Date: 2026-11-17
Status: approved 2026-11-17

## Intent

Replace the `CharacterController`-based movement with a **dynamic Rigidbody capsule** driven by
Source-engine-style (CS2) velocity control plus a sprint, and split movement from input so an AI can
later drive the same movement code. Ship the input layer with rebindable controls persisted to disk;
the Settings screen itself comes later.

Why: the game should feel like CS2, the player should be a real physics body so props/explosions can
shove it and a ragdoll can replace it on death later, and enemies should not need a second movement
implementation.

## Goals

- Real dynamic `Rigidbody` player capsule with custom velocity control (no `CharacterController`).
- CS2 baseline: run, jump, crouch, Source ground friction/acceleration, air acceleration/air-strafing,
  step-up, slope sliding, no auto-bhop.
- Crouch state replicated so server/remote proxies resize their capsule for hit validation.
- Sprint as the one non-CS2 addition: ~8 m/s, forward-only, ground-only, no stamina.
- Movement core that has **no** dependency on Input System, networking, camera or player prefabs.
- One input reader for movement/look/weapons and a rebinding service with persisted overrides and
  reset/conflict handling.
- Player prefab, editor generator (`Anime FPS > Run All`) and respawn updated to the new body.
- Automated tests for movement, AI-driven movement, and binding persistence.

## Non-goals

- Slide, mantle/vault, ladders, swimming, moving platforms, wall-running, stamina.
- Ragdolls (only the body architecture to support them later).
- Client prediction, server reconciliation, lag compensation. Movement stays owner-authoritative.
- Settings UI, key icons, gamepad layout switching UI, control-scheme wizard.
- Mouse sensitivity/invert settings (belongs to the later Settings pass).
- Animation work for crouch/sprint; the existing walk animator int is preserved.
- ADS, weapon sway, sprint affecting weapon accuracy.

## Anti-goals

- Shipping CS2-flavoured numbers on top of `CharacterController` and calling it physics-based.
- A movement class that reads `PlayerInput`, a camera, `Health` or `NetworkBehaviour` in the same file.
- Two movement implementations (player vs AI).
- Silent input rebinding that can leave two actions on the same key without a defined rule.

## Constraints

- Unity 6.6.9f1, URP, Input System 1.20.1, Netcode for GameObjects 2.14.0. No new packages.
- Fixed timestep is 0.02 s (50 Hz); movement runs in `FixedUpdate`.
- The player prefab is generated by `Assets/_Project/Editor/ProjectSetup.cs`; `Run All` rebuilds it.
- `PlayerRespawn`, `PlayerLook`, `PlayerWeapons`, `WeaponHud`, `Health` and existing PlayMode tests must
  keep working; `PlayerMotor` stays the component name on the prefab.
- Owner-authoritative movement + `NetworkTransform` is the current network model and stays.

## Approaches

1. **Dynamic Rigidbody + custom Source velocity control (chosen).** The body is a non-kinematic
   `Rigidbody` with frozen rotation. Every physics step we apply CS2 friction/acceleration/jump/gravity
   to `linearVelocity` ourselves and let PhysX resolve collisions. Gives exact feel, real prop shoving
   and a ragdoll-ready body. Cost: ground/step/slope handling that `CharacterController` gave for free.
2. **Simulated kinematic capsule.** Custom sweep/collision integration, no Rigidbody. Simplest for
   deterministic feel and networking, but the player cannot be shoved by physics or turned into a
   ragdoll. Rejected: conflicts with the stated ragdoll/physics intent.
3. **Keep `CharacterController`, retune numbers.** Lowest risk, but is not physics-based, cannot be
   pushed, and cannot ragdoll. Rejected.

Network sync considered: `NetworkTransform` (chosen, owner writes the body) vs `NetworkRigidbody`
(server-simulated physics, rejected — movement is client-authoritative by design and server simulation
would invalidate the feel).

## Design

### Architecture

```
Human input ─┐
             ├─ MovementIntent ──> CharacterMovement ──> Rigidbody (capsule)
AI brain ────┘                        (no input/net)          │
                                                              ├─ NetworkTransform (owner → remotes)
PlayerMotor (owner glue, NetworkBehaviour)                     └─ future ragdoll on death
  ├─ reads InputReader, checks Health, builds MovementIntent
  └─ owns animator walk int
PlayerLook (owner glue) ── yaw on body Rigidbody, pitch on camera pivot
```

- `CharacterMovement` is a plain `MonoBehaviour` on any GameObject with a `Rigidbody` + `CapsuleCollider`.
- Humans and AI both just call `movement.SetIntent(...)`; nothing else is shared differently.
- `PlayerMotor` is the only owner/network glue and stays the prefab component the tests look for.

### Movement core (`Scripts/Movement/`)

`MovementIntent` (readonly struct):

```csharp
public struct MovementIntent
{
    public Vector3 WishDirection; // world space, Y ignored, ClampMagnitude 1
    public bool Sprint;           // held
    public bool Crouch;           // held
    public bool Jump;             // pressed this step; consumed by the motor
    public static MovementIntent None => default;
}
```

`CharacterMovement` public surface:

```csharp
public MovementProfile Profile { get; set; }
public MovementState State { get; }              // flags + speeds for animation/audio
public bool IsGrounded { get; }
public bool IsCrouching { get; }
public bool IsSprinting { get; }
public bool IsSliding { get; }
public float HorizontalSpeed { get; }
public Vector3 Velocity { get; }
public void SetIntent(in MovementIntent intent);
public void Teleport(Vector3 position, Quaternion rotation); // clears velocity
public void AddImpulse(Vector3 deltaVelocity);                // explosions/knockback, m/s
public event Action Jumped;
public event Action<float> Landed;                            // impact speed
```

Intent is set from `Update` (human) or AI logic; the motor latches `Jump` until the next
`FixedUpdate` consumes it, and holds the rest until replaced.

`MovementProfile` (`ScriptableObject`, `[CreateAssetMenu]`, asset at
`Assets/_Project/Settings/Movement/DefaultMovementProfile.asset`) holds every tunable. Defaults
(Source units converted at 1 unit = 0.0254 m):

Physics step order in `FixedUpdate`:

0. Read the Rigidbody's current `linearVelocity` as the working velocity. Never cache intent
   velocity between ticks: PhysX contact response, prop hits and impulses must survive.
1. Refresh grounded state (ground probe + contact normal).
2. Resolve crouch transition/uncrouch (headroom check).
3. Consume jump buffer/coyote → set vertical velocity to `sqrt(2 * gravity * jumpHeight)`.
4. If grounded and not jumping: Source friction, then ground accelerate toward
   `Sprint ? sprintSpeed : Crouch ? crouchSpeed : runSpeed`.
5. Else: air accelerate toward `min(wishSpeed, airSpeedCap)`; no air friction.
6. Apply custom gravity, clamp to terminal velocity.
7. Step-up if a ≤`stepHeight` face blocks horizontal movement and headroom is clear.
8. Apply the working velocity to the Rigidbody; slope slide adds downhill acceleration when grounded
   on ground steeper than `slideAngle`. Never replace velocity that PhysX set this tick with a value
   computed from intent alone.
9. Ground snap when grounded, not jumping and `verticalVelocity <= 0`.

Source acceleration math (behaviour-defining):

```
friction:  control = max(horizontalSpeed, stopSpeed)
           drop    = control * friction * dt
           newSpeed = max(speed - drop, 0)   // scale horizontal velocity
accelerate: currentSpeed = dot(horizontalVelocity, wishDir)
            addSpeed = wishSpeed - currentSpeed
            if addSpeed > 0:
                accelSpeed = min(accel * wishSpeed * dt, addSpeed)
                horizontalVelocity += wishDir * accelSpeed   // vertical untouched
```

This exact friction→accelerate order is what makes counters, stops and air-strafing feel Source-like.
Do not add Unity drag, friction material or gravity on top.

External velocity: because every tick starts from the Rigidbody's actual velocity, a prop hit, another
player pushing or a physics explosion changes movement without special handling. Source acceleration
only *adds* toward the wish speed, so external speed above the cap is preserved and decays through
friction. `AddImpulse(Vector3 deltaVelocity)` adds a direct m/s delta to `linearVelocity` (mass
independent, not N·s) and, if the delta has an upward component, starts a short (~0.15 s) window that
suppresses ground-stick/snap so a grounded player can actually be launched. Horizontal knockback is
left to normal ground friction (it stops fast, CS-style).

### Collision, grounding and body

- Root `Rigidbody`: mass 80, `useGravity = false`, `freezeRotation = true`, `interpolation =
  Interpolate`, `collisionDetectionMode = ContinuousSpeculative`, zero damping.
- `CapsuleCollider` (height 1.8, radius 0.3, center y 0.9) replaces `CharacterController`. A
  `PlayerPhysicsMaterial` with friction 0, bounciness 0, `FrictionCombine = Minimum` prevents PhysX
  friction fighting our model.
- Ground probe: `Physics.CapsuleCast`/`SphereCast` downward from the capsule bottom, layer mask
  `~Player` (new `Player` layer) and skip triggers; grounded requires a hit with
  `Vector3.Angle(hit.normal, up) <= maxSlopeAngle`. Keep a ~0.1 s grounded grace to avoid flicker on
  steps.
- Step-up: probe forward at ankle height for a blocking face no taller than `stepHeight`; verify
  headroom with a capsule overlap; raise the body and continue. No vertical velocity change.
- Crouch: shrink capsule to 1.2 m and lower the collider center; eye height lerps over
  `crouchTransition`; standing requires a clear capsule overlap above.
- Slope: if ground angle > `slideAngle`, treat as not grounded, skip friction and accelerate downhill
  along the projected plane.
- Physics interactions are allowed: collisions with props/explosions resolve through PhysX; an
  explicit `AddImpulse` feeds external velocity that the movement loop never overwrites from intent.
- Collider stays enabled on remote copies so shots still hit them.

### Player glue and networking

- `PlayerMotor` (rewritten): `NetworkBehaviour`, owner-only. Reads `InputReader` + `Health`, builds
  `MovementIntent` in `Update` from camera-relative WASD, holds sprint/crouch, passes jump edge.
  Keeps the existing `Status_walk` animator int (1 when horizontal speed > ~0.1, else 0).
- `PlayerLook`: unchanged responsibilities, but yaw is applied through the Rigidbody
  (`rb.MoveRotation` in `FixedUpdate`) so interpolation stays coherent; pitch/recoil stay on
  `CameraPivot` in `Update`.
- `OnNetworkSpawn`: non-owner → disable `CharacterMovement`/`PlayerLook`, set `rb.isKinematic = true`,
  but keep `PlayerMotor` enabled (it must receive the crouch `NetworkVariable`); owner → dynamic body.
  Owner-only input/health logic inside `PlayerMotor` is guarded by `IsOwner`.
  `NetworkTransform` keeps owner authority.
- Death: `PlayerMotor` clears intent and pauses `CharacterMovement` (velocity cleared), no movement.
  Ragdoll swap is a later death hook.
- Crouch replication: `PlayerMotor` owns `NetworkVariable<bool> Crouched` (owner write) and mirrors the
  owner's crouch state into it. On non-owners `PlayerMotor` stays alive only to apply the value to the
  local capsule (instant resize, no camera work) so the server proxy used for re-raycast hit validation
  and other clients' hitboxes match the owner. The network code stays in `PlayerMotor`;
  `CharacterMovement` only exposes a way to apply crouch dimensions. Replication is not lag
  compensated — proxies see the owner's crouch one RTT late, which is accepted.
- `PlayerRespawn`: replace the `CharacterController` enable/disable dance with
  `CharacterMovement.Teleport(spawnPosition, spawnRotation)`.
- `PlayerWeapons`/`PlayerLook` get input from `InputReader` instead of calling
  `GetComponent<PlayerInput>().actions[...]` themselves.

### Input system (`Scripts/Input/`)

`InputReader` (MonoBehaviour, owner only):

- Cache the `Player` map actions once from the prefab's `PlayerInput`.
- Expose read properties: `Move` (Vector2), `Look` (Vector2), `SprintHeld`, `CrouchHeld`,
  `JumpPressed`, `AttackHeld`, `AttackPressed`, `ReloadPressed`, `CycleNextPressed`,
  `CyclePreviousPressed`, `ScrollY`.
- `PlayerMotor`, `PlayerLook` and `PlayerWeapons` consume it; no other script touches
  `UnityEngine.InputSystem` except the rebinding service.

`PlayerInputBindings` (static facade, service-like):

```csharp
public enum RebindOutcome { Success, ConflictResolved, Canceled, Failed }

public struct RebindResult
{
    public RebindOutcome Outcome;
    public string[] ClearedBindings; // "ActionName#bindingIndex" for every cleared conflict
}

public static void EnsureLoaded(InputActionAsset asset);        // apply saved overrides once
public static bool BeginRebind(InputActionAsset asset, string actionName, int bindingIndex,
                              Action<RebindResult> completed);
public static void CancelRebind();
public static void ResetBinding(InputActionAsset asset, string actionName, int bindingIndex);
public static void ResetAllBindings(InputActionAsset asset);
public static string ExportOverrides(InputActionAsset asset);   // test seam
public static void ImportOverrides(InputActionAsset asset, string json);
```

- Interactive rebinding uses `InputAction.PerformInteractiveRebinding(bindingIndex)` with
  `WithCancelingThrough("<Keyboard>/escape")`, mouse-position excluded, and a short
  `OnMatchWaitForAnother`.
- Conflict rule: after the new binding resolves, scan **every binding of every action in the Player
  map** by effective path (defaults and overrides together). The new binding wins. Every other binding
  resolving to the same control is explicitly **unbound** with an empty-path override — including a
  binding that had no override before, so removing the override would not have been enough — and
  reported in `ClearedBindings` with `ConflictResolved`. Escape is reserved for cancel and is never
  stolen. Composite parts (WASD) are rebindable and clearable individually; the rest of the composite
  stays intact. Reset restores defaults.
- Persistence: `asset.SaveBindingOverridesAsJson()` to
  `PlayerPrefs["animefps.input.bindings.v1"]`; `EnsureLoaded` disables/re-enables the map and calls
  `LoadBindingOverridesFromJson`, so it is safe to call on startup and after bindings change.
  `ResetAllBindings` clears the key and calls `RemoveAllBindingOverrides`.
- `BeginRebind` disables the `Player` map while listening and re-enables it afterwards, so the action
  under test cannot fire gameplay.
- No UI yet. The later Settings screen calls this facade; it is the only contract.

### AI reuse contract

An AI only needs a `Rigidbody` + `CapsuleCollider` + `CharacterMovement` and a loop that calls:

```csharp
movement.SetIntent(new MovementIntent {
    WishDirection = steeringDirection, // world space
    Sprint = wantsToSprint,
    Crouch = wantsToCrouch,
    Jump = wantsToJumpThisStep,
});
```

No Input System, `PlayerMotor`, camera, or `NetworkBehaviour` references. Yaw is the AI's steering
concern (`Rigidbody.MoveRotation`), as the motor never turns the body. This is proven by a test that
spawns a bare-bodied object, feeds intents and asserts movement.

### Prefab and editor generator

- `ProjectSetup.BuildPlayerPrefab()`: remove `CharacterController`; add `Rigidbody` (settings above),
  `CapsuleCollider` + zero-friction material, `CharacterMovement` + default profile, `PlayerInput` as
  today, and an `InputReader`; wire `PlayerMotor`/`PlayerLook`/`PlayerWeapons` to it.
- Ensure the `Player` layer exists and assign it to the prefab; create the default
  `MovementProfile` asset only if missing (Inspector edits survive `Run All`, matching weapon assets).
- Update `PlayerRespawn` wiring from `controller` to `movement`.
- Prefab is regenerated with `Anime FPS > Run All`; no hand-authored scene changes besides layers.

### Testing

PlayMode tests (existing assembly):

- Bare-body motor: accelerates to ~run speed, sprint reaches ~8 m/s, clearing intent with friction
  stops it, jump apex ≈ 1.45 m, air-strafe gains lateral speed, crouch height/uncrouch blocked,
  0.3 m step climbed, >slideAngle slope slides, `Teleport` clears velocity, `AddImpulse` moves the
  body.
- AI reuse: scripted intent moves a non-player object the same way.
- Input bindings: overrides survive export/import, reset restores defaults, duplicate binding resolves
  to one control, saved JSON loads into a fresh asset copy, cross-action conflicts unbind the losing
  binding even when it was a default, and the unbound state survives save/load.
- Crouch replication: applying replicated crouch to a proxy resizes its capsule (owner and remote
  paths), and the server proxy used for re-raycasts sees the crouched height.
- Existing `PlayerSmokeTests` still find `PlayerMotor`, `PlayerLook`, `PlayerInput`; add assertions
  for `Rigidbody` + capsule and owner-dynamic/remote-kinematic.
- Interactive rebind capture is covered by a focused test using Input System's test fixture if it is
  practical in PlayMode; otherwise the override/conflict/persistence layer is automated and capture is
  a manual check (builder decides, flag it in the plan).

## My calls (correctable)

- Sprint is 8 m/s, forward-only (dot ≥ 0.7), ground-only, no stamina, keeps momentum when jumping.
- Jump is CS2 height (1.45 m) with a 0.1 s jump buffer and 0.05 s coyote time (set 0 for stricter CS2).
- No auto-bhop; air-strafing is preserved exactly.
- Step height 0.40 m; slopes over 50° slide; player mass 80 kg.
- Player becomes a new `Player` layer; ground probes ignore it.
- `CharacterMovement` is passive (push intent in) rather than owning an intent source — simplest for
  AI and tests.
- `AddImpulse` takes a direct m/s delta rather than a force/impulse; upward impulses briefly suppress
  ground snap.
- Movement stays owner-authoritative on `NetworkTransform`; no server reconciliation now.
- Input Reader centralizes weapon input too; mouse sensitivity/invert wait for the Settings pass.
- Rebinding conflicts: cross-action, new binding wins, losing binding explicitly unbound and reported;
  Escape never stolen.
- Crouch is networked via a `PlayerMotor` `NetworkVariable` so server hit validation sees a crouched
  body; proxies apply it instantly, no lag compensation.
- Crouch/sprint animation is out of scope; only the existing walk int is driven.
- Settings UI is out of scope; the static facade is the deliverable.

- Final numbers after a feel pass in the editor; the profile values above are the starting point.
