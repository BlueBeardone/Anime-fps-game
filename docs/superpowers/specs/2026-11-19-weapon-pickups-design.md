# Anime FPS Game — Weapon Pickup Design

Date: 2026-11-19
Status: approved and implemented

## Intent

Put guns on the range that the player can walk up to and swap into their hands. When the player is
close to a ground gun, the HUD shows that gun's picture at the bottom of the screen with the line
"Press F to switch", the way Call of Duty does. Pressing F takes the ground gun into the held slot and
drops the gun that was in that slot on the ground, so every weapon stays in the world and can be
picked back up.

Why now: the four guns, slot switching, multiplayer, the HUD and the world-building generator all
exist. Ground pickups are the missing loop that turns the fixed loadout into something you interact
with, and they are the foundation for later ammo, attachments and loot.

## Goals

- Four ground guns on the range, one per existing archetype: Rifle (K98), Handgun (Luger P08),
  SMG (MP40), Shotgun (K98 placeholder). They are visible, networked, and placed near the spawn and
  down-range so the player meets them immediately.
- Proximity prompt: within `pickupRadius` the HUD shows a picture of that exact gun and
  "Press F to switch". It disappears when the player walks away, dies, or is already holding the same
  archetype.
- Press F swaps: the held slot takes the ground gun's archetype and the previously held archetype is
  dropped at the player's feet as a new ground gun.
- Ammo is counted: a ground gun carries its own magazine and reserve. Picking it up gives you exactly
  the rounds it was holding, and the gun you drop keeps exactly the rounds you had left. Nothing is
  refilled by swapping.
- Every peer sees the same world: consumed guns disappear for everyone; dropped guns appear for
  everyone. Two players cannot take the same gun.
- If several guns are in range, the prompt shows the nearest one, and F takes that one.
- Owner-only HUD; remote players still see the correct held weapon mesh on the body after a swap.
- Everything survives `Anime FPS > Run All`, because `ProjectSetup` generates it.

## Non-goals

- Pickup-only special weapons (MG42, STG44, Panzerfaust, Flammenwerfer) and rocket/flame archetypes.
- Ammo pickups, ammo boxes, or refilling any gun without a swap.
- Attachments, skins, rarity, loot tables, weapon throwing, drop-on-death.
- Pickup audio, authored pickup animations, outline/highlight shaders.
- Client prediction of the swap. The swap is server-authoritative and lands one RPC round-trip later.
- Persisting a custom loadout across sessions or respawns. Respawn keeps the current carried loadout.

## Anti-goals

- A client-local pickup that only its own player sees and that lets two players take one gun.
- A second HUD system. The prompt and icon live inside the existing runtime-built `WeaponHud`.
- Hand-edited scene or prefab state that `ProjectSetup` would overwrite. Any prefab, scene object,
  input action or network-prefab registration must be generated by `ProjectSetup`.
- Per-frame RenderTexture rendering. The gun picture is re-rendered only when the nearby gun changes.
- A duplicate mapping of gun visuals. Ground visuals, held viewmodels and the HUD icon all resolve from
  the existing `WeaponDefinition` catalog and the existing gun prefabs.

## Constraints

- Unity 6000.6.9f1, URP, Input System 1.20.1, Netcode for GameObjects 2.14.0.
- `Assets/_Project/Editor/ProjectSetup.cs` is the authoritative generator; `Run All` rebuilds the
  scene, NetworkManager, player prefab and menu. All new wiring must be idempotent.
- The player prefab already holds four `WeaponDefinition` slots and one `IGun` per slot. Slot contents
  are currently fixed; this feature makes them mutable and networked.
- `GunArchetype` has exactly four values today and each catalog entry maps to a distinct archetype.
- `DefaultNetworkPrefabs.asset` (`NetworkPrefabsList`) is referenced by `NetworkConfig.NetworkPrefabsLists`.
  Runtime drops need the pickup prefab registered there.
- Scene `NetworkObject`s (the dummies, the pickups) auto-spawn through NGO scene management.
- Existing PlayMode tests must keep passing.

## Approaches

1. **Local-only pickups.** Ground guns are plain scene props; each client detects proximity and swaps
   its own slot, hiding the prop locally. Cheapest, perfect solo, but joining clients see stale guns
   and two players can take the same one.
2. **Networked pickup objects (chosen).** Each ground gun is a `NetworkObject`, like the dummies.
   Pressing F sends a server RPC; the server validates distance, despawns that pickup, swaps the
   player's networked slot contents, and spawns the dropped gun. Everyone sees the same world.
3. **Server-managed pickup pool.** One manager owns a `NetworkList` of pickup states and reuses a
   fixed pool of visuals. Avoids runtime network spawning but is bespoke and more code for the same
   behaviour as 2.

Why 2 wins: it reuses the scene-`NetworkObject` pattern already proven by `TargetDummy`, keeps
authority on the server without inventing a pool, and lets a dropped gun be a first-class object at an
arbitrary position. Approach 1 was rejected because it breaks multiplayer fairness; approach 3 was
rejected as unnecessary indirection.

## Decisions made with the human

- Swap and drop, not replace-and-vanish.
- Networked pickup objects (approach 2).
- Different weapons placed on the range as pickups.

## Design

### Pickup identity

A ground gun is identified by `GunArchetype` (byte on the wire). The four archetypes are unique in the
player catalog, so the archetype resolves to one `WeaponDefinition` everywhere. No new catalog asset
and no extra id table are introduced.

### Player loadout becomes mutable and networked

`PlayerWeapons` keeps its serialized `WeaponDefinition[] slots` as the **catalog and initial loadout**
(unchanged asset references). It gains:

```csharp
readonly NetworkList<byte> carriedArchetypes = new();
```

- Server populates `carriedArchetypes[i]` from `slots[i].stats.stats.archetype` when the player object
  spawns, so the initial loadout is explicit and replicated.
- `carriedArchetypes` is server-written and read by everyone. Clients resolve the visible weapon mesh
  for the active slot from it, so a swapped gun looks right on remote bodies.
- `DefinitionFor(GunArchetype)` returns the matching `WeaponDefinition` from `slots`; it is the single
  mapping used by the swap, the HUD icon and the world mesh.
- `guns[i]` (the live `IGun` instances) stays one per carry position and is built on **every peer**,
  exactly as `BuildGuns` does today. Only the owner ticks them for firing. The server's array is not
  optional: `FireServerRpc` reads `guns[slot].Stats` and the per-slot cadence arrays to validate
  every remote client's shots, so removing server-side `IGun` construction would reject all remote
  fire. When a slot's archetype changes, every peer rebuilds that slot's gun from the new definition
  (owner and server included), cancels any reload, and re-applies the viewmodel if the slot is active.
  Remote peers only use the rebuilt instance for the body mesh, but keeping the array in sync costs
  nothing and keeps server validation correct.
- `SwapSlotServer(byte slot, GunArchetype incoming, int incomingMagazine, int incomingReserve)`
  is server-only: reads the outgoing archetype, writes the new one, and returns the outgoing
  archetype. The resulting `carriedArchetypes` change rebuilds the slot's `IGun` on every peer through
  the same change handler.
- Ammo survives a swap in both directions. `IGun`/`Gun` gain
  `RestoreAmmo(int magazine, int reserve)`, which clamps to the gun's stats and raises the existing
  ammo/reload events. The owner restores the incoming pickup's rounds into the new gun; the outgoing
  rounds are written onto the dropped pickup.
- Ammo stays **owner-authoritative**, matching the existing accepted tradeoff. The owner sends its
  held magazine/reserve with the pickup request, so the drop carries the real numbers rather than the
  server's unticked copy. The server clamps them to the outgoing gun's `magazineSize`/`reserveAmmo`
  before storing them, so a malformed report cannot create an oversized drop. Remote peers build the
  swapped gun full because they never fire it; only the owner's ammo is meaningful.
- The owner caches the target pickup's `MagazineAmmo`/`ReserveAmmo` when it sends the request. When the
  `carriedArchetypes` change arrives for that slot, it rebuilds the gun and restores the cached values.
  Caching at request time avoids a return RPC and any ordering race between the list delta and a
  result message. On the host, server and owner are the same instance, so the same handler restores
  the ammo directly.
- Fallback: before `carriedArchetypes` has synced, `ApplySlot` falls back to the serialized slot, so
  the first frames and a disconnected editor never show a missing gun.

Existing slot cycling (`1`/`2`, Next/Previous, wheel) is unchanged. The active slot is still an
owner-written `NetworkVariable<byte>`.

### Ground pickup object

One prefab, `Assets/_Project/Prefabs/Weapons/WeaponPickup.prefab`, generated by `ProjectSetup`:

- Root: `NetworkObject`, `WeaponPickup` (`NetworkBehaviour`).
- Serialized `initialArchetype` (used by the scene instances placed by `ProjectSetup`).
- Serialized table mapping each `GunArchetype` to a world gun prefab
  (`K98_prefab`, `LugerP08_prefab`, `MP40_prefab`, `K98_prefab` for the Shotgun placeholder).
- `NetworkVariable<byte> archetype`, server-written. Runtime drops set it before `Spawn()`; scene
  instances copy `initialArchetype` into it in `OnNetworkSpawn` on the server.
- `NetworkVariable<int> magazineAmmo` and `NetworkVariable<int> reserveAmmo`, server-written and
  readable by everyone, so the HUD/owner can show and take the exact rounds on the ground.
  - Scene instances start full from the archetype's `GunStats.magazineSize`/`reserveAmmo`.
  - Runtime drops carry the outgoing gun's clamped magazine/reserve as described above.
- On every peer, `OnNetworkSpawn` instantiates the matching world gun prefab under a `Visual` child,
  scaled to world size, lying flat with a slight tilt and a slow yaw spin so it reads as a pickup.
  No collider is required; proximity uses the registry below.
- `SpawnTime` is recorded on spawn on both the server and each client (local `Time.time`). A
  **runtime drop** is in its **drop cooldown** for `dropCooldown` (0.75 s) after it spawns. This one
  timer is the only cooldown in the feature: it blocks that pickup and nothing else. Scene pickups are
  not runtime drops and are usable the moment the match starts.
- A static `All` registry (add on `OnNetworkSpawn`, remove on `OnNetworkDespawn`) is the lookup used by
  players and by the server.

Scene placement (by `ProjectSetup`, idempotent by object name): four pickup instances, one per
archetype, on the range near the spawn points and the dummies — for example Rifle at (1.5, 0.2, -2),
Handgun at (-1.5, 0.2, -2), SMG at (3, 0.2, 4), Shotgun at (-3, 0.2, 4). Exact spots are tuning.

### Proximity and input

New `PlayerPickupInteractor : NetworkBehaviour` on the player prefab:

- Owner only. Each frame it scans `WeaponPickup.All`, keeps the nearest spawned pickup whose horizontal
  distance is within `pickupRadius` (3 m default), and ignores pickups still in their drop cooldown, so
  the prompt never invites a pickup the server will refuse.
- If the nearest pickup's archetype equals the player's held archetype, it publishes no target, so the
  prompt does not invite a no-op swap.
- Exposes `NearestPickup` and `NearestArchetype` for the HUD. A static helper
  `FindNearest(Vector3 playerPosition, IEnumerable<...>)` is separated out so the nearest-in-range
  rule is testable without a scene.
- On `input.PickupPressed` with a target, it caches the pickup's current magazine/reserve and sends
  `TryPickupServerRpc(pickup.NetworkObjectReference, outgoingMagazine, outgoingReserve)`, where the
  outgoing values come from the owner's held `IGun`.

New input action `Pickup` on the `Player` map, bound to `<Keyboard>/f` and `<Gamepad>/buttonNorth`.
`InputReader` exposes `PickupPressed`. The unused `Interact` action is left untouched.

### Server swap

In the server RPC, the server validates before changing anything:

- the player is spawned and alive;
- the pickup exists in `WeaponPickup.All`, is spawned, and is not already despawned;
- the pickup is within `pickupRadius + 0.5 m` of the player's server-side position;
- the pickup's archetype differs from the held slot's archetype;
- the pickup is not inside its own drop cooldown on the server (the same 0.75 s, measured from the
  server's spawn time for that object). This is the only cooldown check; there is no separate
  per-player timer.

Then the server, in order:

1. Reads `slot = activeSlot.Value` and the outgoing archetype, and clamps the reported
   `outgoingMagazine`/`outgoingReserve` to that gun's `magazineSize`/`reserveAmmo`.
2. Calls `weapons.SwapSlotServer(slot, pickup.Archetype, pickup.MagazineAmmo, pickup.ReserveAmmo)` and
   receives the outgoing archetype.
3. Despawns the consumed pickup with `Despawn(true)`.
4. Instantiates `pickupPrefab`, sets its archetype, magazine and reserve to the outgoing/clamped values,
   positions it at `player.position + flatForward * 0.75` at ground level, and `Spawn()`s it.

The server keeps at most 12 runtime-dropped pickups; beyond that it despawns the oldest runtime drop
(scene pickups are never culled). This keeps repeated swaps from filling the map.

### HUD prompt and gun picture

`WeaponHud` grows one bottom-centre block, built in code like the rest of the HUD:

```
            +----------------------------+
            |      [ picture of gun ]    |
            |         SHOTGUN            |
            |      Press F to switch     |
            +----------------------------+
```

- A dark translucent panel anchored bottom-centre, around y = 200 (above the reload bar at y = 90),
  with a `RawImage` (~220x110), the weapon's display name in a small caption, and a one-line `Text`
  "Press F to switch". Hidden by default.
- The display-name caption is required because the Shotgun borrows the K98 art: without it the Rifle
  and Shotgun prompts would be pixel-identical. The name comes from `WeaponDefinition.displayName`
  ("Rifle", "Handgun", "SMG", "Shotgun").
- The picture is a `RenderTexture` (512x256, transparent clear) produced by a small preview rig owned
  by the HUD: an orthographic/perspective camera plus a point light, placed 1000 m below the map so
  nothing else is in frame and the main camera never sees it. The preview gun is instantiated from
  `DefinitionFor(archetype).viewmodelPrefab`, auto-fitted to the frame from its renderer bounds.
- The rig is rebuilt only when `NearestArchetype` changes, not per frame. A null target hides the
  block and releases the preview instance.
- The block also hides while dead, matching the existing HUD behaviour, and on remote clients the
  whole canvas is already disabled.

The prompt wording stays "Press F to switch" as requested; the picture plus the display-name caption
carry the identity.

### ProjectSetup changes

All idempotent additions to `Editor/ProjectSetup.cs`:

- regenerate the weapon pickups and register the pickup prefab in `DefaultNetworkPrefabs.asset` via
  `NetworkPrefabsList.Add(new NetworkPrefab { Prefab = ... })`, skipping if `Contains` is true;
- create `WeaponPickup.prefab` once with the archetype→world-prefab table filled from the existing
  gun prefabs (reuse `EnsureViewmodel`-style copy/load, not new art);
- add `PlayerPickupInteractor` to the generated player prefab, wire `weapons`, `input`, the pickup
  prefab and the radius;
- add the `Pickup` action to `InputSystem_Actions.inputactions` if missing, mirroring
  `EnsureReloadAction`;
- place the four scene pickup instances on the range without duplicating them on re-run;
- leave existing slots, stats assets, dummies and build order untouched.

### Tests (PlayMode, matching existing style)

- `Main` scene contains four spawned pickups with four distinct archetypes, each registered in
  `WeaponPickup.All`.
- The pickup prefab is a registered network prefab (a runtime instantiation+spawn succeeds).
- `FindNearest` picks the closest in-range pickup, returns null when all are out of range, and ignores
  pickups inside their drop cooldown.
- A spawned player has `PlayerPickupInteractor`, and the `Pickup` action exists on the Player map.
- `SwapSlotServer` changes the carried archetype and the owner's active `IGun` archetype, and returns
  the outgoing archetype. Running `SwapSlotServer` twice restores the original. The server's
  `guns[slot].Stats` must match the incoming archetype, because remote shot validation reads it.
- Ammo round-trip: put a partially spent gun in a slot, swap it for a ground gun, and assert the
  incoming gun has the ground pickup's magazine/reserve while the new drop carries the exact
  magazine/reserve that was in the slot. `RestoreAmmo` clamps values above the stats.
- Host pickup flow: teleport the host player next to a scene pickup, trigger the server pickup path,
  assert the pickup despawns, the held archetype changes, the held ammo matches the pickup's counts,
  and a new pickup with the outgoing archetype and outgoing ammo exists at the player's feet and is
  not immediately re-pickable.
- HUD prompt is hidden when there is no target and visible when a target is published (test through a
  small public API rather than pixel inspection).
- Existing player, HUD, gun, input and movement tests stay green.

## My calls (correctable)

- Pickup identity is `GunArchetype`, not a new id or catalog asset, because the four current entries
  are unique archetypes.
- Ammo is counted across a swap and stays owner-authoritative: the owner reports its held rounds,
  the server clamps them for the drop, and the owner restores the pickup's rounds from values cached
  at request time. No return RPC is needed.
- Scene pickups start full; the prompt does not show round counts (the HUD ammo readout shows them
  once the gun is in your hands).
- Ground visuals are the full world gun prefabs (the same ones the soldier holds), not new art.
- The HUD icon renders the real `viewmodelPrefab` into a RenderTexture, refreshed only on target
  change, using a preview rig 1000 m below the map with a point light.
- Drop position is at the player's feet, 0.75 m forward, with a single per-pickup 0.75 s spawn
  cooldown (client prompt and server validation both use it). Scene pickups sit at authored spots.
- Runtime drop cap is 12; scene pickups are never culled.
- Prompt says exactly "Press F to switch", with the weapon's display name as a small caption above it
  so the Rifle and Shotgun (which share art) are distinguishable.
- `BuildGuns` keeps running on every peer so the server retains the `IGun.Stats` its remote fire
  validation depends on; only the owner ticks guns.
- The new action is F / gamepad north; the unused `Interact` action is not repurposed.

## What is left to the builder

- Exact scene pickup positions, ground-gun tilt/height/scale and spin speed after looking at them in
  the range.
- Preview camera distance/FOV and background dimming so each gun reads well at 220x110.
- Whether a gentle bob or a light pulse is added to ground guns.
- Whether the prompt should also fade in/out or snap; first pass snaps.
- The exact drop offset if 0.75 m feels wrong around dummies or walls.

## Risks

- `NetworkList<byte>` initialization order: mitigate by writing on the server at spawn and falling
  back to the serialized slot until synced.
- Runtime-spawned network prefab registration is easy to get wrong; the scene test and NGO error logs
  are the check. If registration proves fragile, the documented fallback is server-spawned prefabs
  owned by a single manager, not a return to client-local pickups.
- The preview rig lives in the world; if the map ever gains geometry 1000 m below the origin, move the
  rig or add a preview layer.
- The player prefab referencing the pickup prefab creates a prefab dependency; both are generated by
  `ProjectSetup`, so ordering in `Run All` must create the pickup prefab before the player prefab.
- Dropped guns can be dropped inside a wall; the server uses the player's position, not a physics
  trace, in this pass.
